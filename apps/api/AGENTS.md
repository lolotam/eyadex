# apps/api rules

- Modules live in `src/modules/<module>/` (domain, ports, persistence, queries, `<module>.module.ts`, `index.ts`); persistence uses only `@eyadex/db` wrappers with bound `sql` — so tenant isolation and the import arrows stay checkable.
- A module reads another module's tables only through a port it defines and the owner implements (tenancy's `SeatUsageReader` ← identity's `PgSeatUsageReader`); allowed arrows are in CLAUDE.architecture.md §2.2.
- Every module imports `DatabaseModule` (one pool, closed on shutdown) — never its own `databaseProvider`.
- `tx.execute` cannot bind a `Date` (postgres.js `unsafe()` sends parameters as text): bind `date.toISOString()` with `::timestamptz`.
- Auth is same-origin per area (ADR-0004): `/auth/*` is an allowlist in `identity/auth/auth-routes.ts`, the area comes only from `AreaHosts.resolve`, and `/v1` routes use `SessionGuard` (area-bound `EyadexAuth.getSession`, never `auth.api.getSession`) — so cookies never cross areas and new Better Auth routes stay closed by default.
- Limited auth routes are counted in Redis by `identity/auth/rate-limiter.ts` before Better Auth is called, with limits only in `auth-rate-limits.ts`, HMAC keys and fail-closed on Redis errors (ADR-0005) — so limits hold across replicas and keys never carry personal data.
- Cross-module side effects are rows in `outbox_events` written in the use case's transaction (`shared/outbox.ts`); a secret an event needs (the invitation link) is sealed with `SecretSealer` (`@eyadex/secrets`, shared with the worker) bound to the event id, never stored in clear (ADR-0006); the worker's dispatcher opens it, re-checks the invitation and scrubs it after the outcome (ADR-0013) — so the database never holds a usable token.
- Clinic onboarding is tenancy's `CreateClinicWithAdmin` on the `eyadex_platform` pool via `withNewTenant`; identity writes roles/invitation/email hold through tenancy's `FirstAdminProvisioner` port, and the platform module only wires HTTP — so the one cross-module write stays in one transaction with the import arrows intact.
- Sensitive creates take a required `Idempotency-Key`, claimed in the same transaction (`shared/idempotency.ts`, scope = operation + actor) — so a replay returns the stored ids and a failed attempt leaves no key behind.
- The production image is `apps/api/Dockerfile` (ADR-0007); a change to apps/api or its workspace dependencies must keep `docker build -f apps/api/Dockerfile .` green (CI `api-image`) — Dokploy deploys exactly that image behind Traefik with `TRUST_PROXY_HOPS=1`.
- Every sessionless `/v1` route is listed in `identity/auth/public-rate-limits.ts` and guarded by `PublicRateLimitGuard` (an unlisted one is refused; a test walks the controllers) — so nothing public escapes the Redis limiter.
- Invitation acceptance never deletes an auth user: the clinic transaction holds the invitation row `FOR UPDATE`, and a clinic account left by a failed attempt of the same link is reused with a new password (ADR-0008) — so every failure is fixed by retrying the link.
- Every route handler declares exactly one of `@Public` / `@Authenticated` / `@Require(key)` / `@PlatformStaff` (`identity/access`); the global `AccessGuard` runs the PRD §4.7 order and a route with none or two fails the boot (ADR-0009) — so no endpoint ships without a guard.
- Use cases receive `ClinicRequestContext` from the guard and never check role names; any change to roles, permissions, memberships, branches or clinic status calls `AuthorizationInvalidator.clinicChanged` after commit (ADR-0009) — so the versioned Redis cache never serves a stale grant.
- A route in a module declares `@RequiresFeature(module)` beside its one access declaration (boot fails otherwise); a locked module's keys are never granted and `role_permissions` rows are never deleted on lock (ADR-0010) — so re-enabling restores the exact previous effect.
- Platform changes to a clinic run on the `eyadex_platform` pool in one transaction with one allowlisted platform audit row, then call `AuthorizationInvalidator.clinicChanged` after commit (log on failure, TTL covers it) — so the next clinic request sees the change.
- Writes that consume a seat or a branch decide the limit inside their own transaction under a per-clinic `pg_advisory_xact_lock`, using `limits.ts`, and reject with `limit_reached` + `limitReachedDetails`; `ClinicLimits` is for read-only displays (ADR-0011) — so parallel creates can never pass the limit together.
- Clinic-side `Idempotency-Key` claims go to `clinic_idempotency_keys` (`shared/clinic-idempotency.ts`, forced RLS), never the platform ledger — so one clinic never reads another's stored responses.
- Users and invitations (ADR-0012): seats and the last-admin rule are decided under the per-clinic `users:` advisory lock (taken before the `branches:` lock when both are needed), the admin is found by its system role key, and deactivation revokes the member's sessions after commit before the cache bump — so parallel writes can never pass the limit or remove the last admin.
- The only response that ever carries an invitation token is `POST /v1/invitations/:id/link` (copy link: rotates the hash, audited, no email); every other invitation response has `token: null`; each send writes one `clinic.user_invited` outbox event with the sealed token, and resend rotates the hash — so only the dispatcher's send-time check (pending, unexpired, hash matches) can ever mail a link.
- tenancy reads membership data only through `ExclusiveMemberReader` (identity's `PgExclusiveMembers`) — so branch rules stay in tenancy without crossing the import arrows.
- A successful branch deactivation appends one `clinic.branch_deactivated` outbox event (`tenancy/events/published.ts`) and tenancy never reads or writes invitations; the worker cancels pending invitations left with no active branch (ADR-0013 §12) — so the rule lives in one place and replays are idempotent.
- Clinic settings live in `settings` (ADR-0014): a module other than identity imports identity only through `identity/index.ts` (guards and request types; `module-boundaries.spec.ts` enforces it), clinic mail credentials are sealed with `MAIL_PROVIDER_SEAL_KEY` bound to the row id and never returned, audited or logged, and an idempotency fingerprint over a secret-bearing body is an HMAC with that key — so neither the table nor the key ledger can leak or be used to guess a credential.
- Staff invitations (`clinic.user_invited`) use the clinic's mail provider only when it is verified and not degraded; three consecutive definitive failures (`worker/invitation-mail/domain/clinic-failure.ts`) degrade it to platform mail on its behalf, and only a successful test send or a replacement recovers it (ADR-0014 7c-2b) — so a failing clinic provider never strands invitations and never switches mid-event.
- Role writes (ADR-0017): only `is_locked` refuses a write (`role_locked`), saved keys keep the existing keys of a switched-off module (`mergeHiddenKeys`, modules read in the transaction), role definition writes need an all-branch actor whose stored keys (every module) cover the role, role grants also need the target's branch scope inside the actor's, decided by `grant-rules.ts` on the actor reloaded after a first `roles:` lock (never the cached context), which must still hold the route's own `@Require` key before any row is written, and `role_in_use` is counted under the `users:` then `branches:` locks (user writes hold the first, invitation acceptance the second) — so a module lock, an over-grant or a racing holder can never change a role behind the admin's back.
- Patients (ADR-0018): nothing personal goes in a URL (the list query is `POST /v1/patients/search`), branch scope per action makes out-of-scope files `not_found`, every open and write adds one `patient_access` row through `shared/patient-audit.ts` with an allowlisted snapshot (no civil ID, no birth date, phone last 3 digits), and the idempotency ledger stores ids only — so a civil ID never reaches logs, URLs, audit snapshots or stored responses.
- Environments (ADR-0021): cookie names come only from `areaCookiePrefix(AUTH_COOKIE_PREFIX, area)` — never a literal `eyadex-<area>` (the rate limiter reads the pending `two_factor` cookie through `AreaAuth.cookiePrefix`) — every answer carries `SECURITY_HEADERS` (`shared/security-headers.ts`), and the first platform account comes only from `dist/bootstrap-platform-account.js` on a database that has none — so staging and production can never read each other's sessions.
- The audit module's SQL names only the audit relations (`audit_log`, `platform_audit_log`, `platform_clinic_admin_audit`, `platform_audit_actors`); member, role, branch and clinic names and the clinic time zone come through its `AuditNameReaders` ports, implemented by identity and tenancy and bound in `audit.module.ts` (ADR-0019 §10) — so the audit log never couples to another module's tables.
- Settings and the platform team (ADR-0020): `@PlatformStaff` also asks `PLATFORM_ACCOUNT_GATE` (a linked, `active` `platform_accounts` row, read on every request; not mounted = 500), platform-global writes (`platform_settings`, `platform_accounts`) run in `withNoTenant` on the platform pool, a clinic changes only its own five `clinics` columns (0036 column grant + policy), and names typed by a person reach audit rows only through `scrubAuditText` — so a deactivated platform account loses access on its next request and no clinic can touch its own subscription.
- Appointments (ADR-0026): the module reads members only through `ProviderDirectory` (identity's `PgProviderDirectory`), branches through `SchedulingBranchReader` and patients' files through `BookingPatientReader` (patients' `PgBookingPatients`, name/file number/status only), all bound in `appointments.module.ts`; every write about one provider (booking profile, weekly schedule, time off, and from A2 the bookings) holds `lockProvider` (`appointments:<clinicId>:<membershipId>`), after the `roles:` / `users:` locks when it needs those — so an overlap is always decided on rows no other transaction can change.
- The `own` scope (ADR-0026 §12): `own` is a view scope only and the wider key wins; appointments narrow by `provider_membership_id` = the caller's membership, patients by one `EXISTS` on a non-cancelled appointment with the caller, which lives only in `patients/queries/own-patients.ts` (the patients module's one read of `appointments`; `module-boundaries.spec.ts`) — so an own-only doctor never sees another provider's bookings or files, and a file it may not see is `not_found`.
- Lock order (ADR-0027): every transaction takes its locks as an ordered subset of `roles:` → `users:` → `patients:` → provider locks (sorted) → an `appointments` row → a membership row (then an invitation row) → a patient row → `branches:` → a branch row → a `clinic_services` row → the `clinics` row, and a row an INSERT will reference through a foreign key is locked explicitly at its place first (`ProviderDirectory.lockForWrite` before `lockForFiling`) — so no two writers can ever wait on each other in a cycle.
