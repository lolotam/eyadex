# Finance F1 — service prices and invoices — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for
> tracking.

**Goal:** Clinics with the `finance` module can price services (base + per-doctor), issue gap-free numbered
invoices per branch from an appointment, a visit or by hand, edit/discount/void them under audit, print them
and send them to the patient by email or WhatsApp with a private link; the platform sees monthly totals only.

**Architecture:** A new `billing` API module (`apps/api/src/modules/billing`) on the medical-module pattern
(domain / ports / persistence / use-cases / http), one pure totals function in `packages/contracts` shared by
the API (and its PDF) and the mock, raw SQL migrations 0060–0063 with RLS + negative tests, the notifications ledger
extended for invoice sends, and the web screens built by Lovable from a brief once contracts are frozen.

**Tech Stack:** TypeScript, Zod (contracts), NestJS on Fastify, Drizzle + raw SQL (PostgreSQL 18, RLS),
vitest, TanStack Start + shadcn/ui (Lovable).

**Spec:** `docs/specs/finance-design.md` at `5f28618` — §3 (F1), §8 Review R1 and §8b Review R2 are
**binding**; where they differ, §8b wins over §8, and §8 wins over §3.

## Global Constraints

- Money is a `bigint` count of minor units; on the wire a decimal integer string (`"12500"`), never `number`
  (R1-2). One line (unit price × quantity, a line discount, a service or doctor price) ≤ 10¹² minor units
  (`minorLineAmountSchema`); every aggregate (subtotal, discounts, tax, total, an invoice discount) ≤ the
  PostgreSQL `bigint` ceiling 9 223 372 036 854 775 807 (`minorAmountSchema`).
- `total_minor = Σ line_total + tax_minor` (R1-1 step 6, fixed in `5f28618`); allocation per R2-1; worked
  examples E1–E6 are the acceptance table.
- Every clinic table: `clinic_id uuid NOT NULL`, PK `(clinic_id, id)`, RLS ENABLED + FORCED, policy
  `clinic_id = NULLIF(current_setting('app.clinic_id', true), '')::uuid` USING + WITH CHECK, indexes start with
  `clinic_id`, every FK indexed, no hard deletes, UUID v7 from the app (CLAUDE.md §5).
- New table ⇒ its RLS negative test in `db/tests/rls-isolation.sql` in the same PR.
- `eyadex_platform` has **no grant** on any finance table; it reads totals only through
  `finance_monthly_totals()` (FIN-3).
- Finance audit rows are `category = 'patient_access'`; snapshots hold ids, numbers and amounts, never patient
  names or free-line text (R1-3).
- Lock order for every money operation: per-clinic advisory lock (only for prices/currency/first issue) →
  patient row → invoice rows by id ascending; `If-Match` checked after the invoice lock (R2-8).
- Permissions are checked, never role names; guard order active user → clinic access → module (`finance`)
  → permission → branch scope (CLAUDE.md §6).
- Every UI string ar + en; «المراجع», never «المريض»; logical CSS only; files ≤ 300 lines; Arabic JSDoc on
  exported functions in `domain/**` and methods in `ports/**`.
- SQL files are forward-only: never edit an applied file. Production SQL needs the owner's explicit sentence.
- Commits end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

```ts
const BP = 10000n;
export function roundHalfUpDiv(n: bigint, d: bigint): bigint {
  return (n * 2n + d) / (2n * d);
}

function discountOf(base: bigint, d: Discount | null): bigint {
  if (d === null) return 0n;
  if (d.kind === "pct") {
    if (!Number.isInteger(d.bp) || d.bp < 0 || d.bp > 10000) throw new TotalsError("invalid_line");
    return roundHalfUpDiv(base * BigInt(d.bp), BP);
  }
  if (d.minor < 0n || d.minor > base) throw new TotalsError("discount_exceeds_total");
  return d.minor;
}

/** R1-1 + R2-1: the one totals function (API and its PDF, mock). */
export function computeInvoiceTotals(input: TotalsInput): Totals {
  const seen = new Set<number>();
  const sorted = [...input.lines].sort((a, b) => a.position - b.position);
  const lines = sorted.map((l) => {
    if (
      seen.has(l.position) ||
      !Number.isInteger(l.quantity) ||
      l.quantity < 1 ||
      l.quantity > 999 ||
      l.unitPriceMinor < 0n
    )
      throw new TotalsError("invalid_line");
    seen.add(l.position);
    const grossMinor = l.unitPriceMinor * BigInt(l.quantity);
    if (grossMinor > MAX_LINE_MINOR) throw new TotalsError("amount_out_of_range");
    const lineDiscountMinor = discountOf(grossMinor, l.discount);
    return {
      position: l.position,
      grossMinor,
      lineDiscountMinor,
      netMinor: grossMinor - lineDiscountMinor,
    };
  });
  const netSum = lines.reduce((s, l) => s + l.netMinor, 0n);
  const invoiceDiscount =
    input.invoiceDiscount === null
      ? 0n
      : netSum === 0n
        ? (() => {
            throw new TotalsError("discount_exceeds_total");
          })()
        : discountOf(netSum, input.invoiceDiscount);
  const shares = lines.map((l) => (netSum === 0n ? 0n : (invoiceDiscount * l.netMinor) / netSum));
  let rest = invoiceDiscount - shares.reduce((s, x) => s + x, 0n);
  while (rest > 0n) {
    for (let i = 0; i < lines.length && rest > 0n; i++) {
      if (lines[i]!.netMinor - shares[i]! > 0n) {
        shares[i] = shares[i]! + 1n;
        rest -= 1n;
      }
    }
  }
  if (!Number.isInteger(input.taxRateBp) || input.taxRateBp < 0 || input.taxRateBp > 10000)
    throw new TotalsError("invalid_line");
  const out = lines.map((l, i) => {
    const lineTotalMinor = l.netMinor - shares[i]!;
    return {
      ...l,
      allocatedMinor: shares[i]!,
      lineTotalMinor,
      taxMinor: roundHalfUpDiv(lineTotalMinor * BigInt(input.taxRateBp), BP),
    };
  });
  const taxMinor = out.reduce((s, l) => s + l.taxMinor, 0n);
  const totalMinor = out.reduce((s, l) => s + l.lineTotalMinor, 0n) + taxMinor;
  return {
    lines: out,
    subtotalMinor: out.reduce((s, l) => s + l.grossMinor, 0n),
    discountMinor: out.reduce((s, l) => s + l.lineDiscountMinor, 0n) + invoiceDiscount,
    taxMinor,
    totalMinor,
  };
}
```

**Closing the direct path:** `eyadex_platform` holds the **table-level** grant `SELECT, INSERT, UPDATE ON
clinics` (0013:34) and the policy `clinics_platform_all` (USING true, WITH CHECK true), so it could change the
currency without the function and its lock. A column-level `REVOKE UPDATE (currency, …)` does **not** remove a
table-level grant (proved below). 0061 changes the effective privilege exactly like this:

```sql
-- Fails the migration if clinics gained a column nobody reviewed for the platform's UPDATE list.
DO $$ DECLARE actual text[]; BEGIN
  SELECT array_agg(column_name::text ORDER BY ordinal_position) INTO actual
  FROM information_schema.columns WHERE table_schema = 'public' AND table_name = 'clinics';
  IF actual <> ARRAY['id','slug','name_ar','name_en','specialty','default_language','timezone','status',
      'expires_at','max_users','max_branches','created_at','updated_at','currency','currency_exponent',
      'tax_rate_bp','commercial_reg_no','logo_blob_key'] THEN
    RAISE EXCEPTION 'clinics columns changed: %', actual; END IF; END $$;
REVOKE UPDATE ON clinics FROM eyadex_platform;                       -- removes the table-level UPDATE
GRANT UPDATE (slug, name_ar, name_en, specialty, default_language, timezone, status, expires_at,
              max_users, max_branches, updated_at, tax_rate_bp) ON clinics TO eyadex_platform;
-- SELECT and INSERT stay table-level (creating a clinic sets its currency; it has no price yet).
```

INSERT **true**. The runtime platform statements (`platform-clinic-changes.ts:134` status/expires_at/updated_at,
`:164` max_users/max_branches/updated_at) all stay inside the list.

### Task 9: Invoice sending and the patient link

**Files:** `billing/use-cases/invoice-send/invoice-send.ts`, `billing/http/invoice-links.controller.ts`,
`apps/worker/src/patient-notifications/**` (invoice kind, link minting), `apps/api/src/modules/identity/auth/public-rate-limits.ts`,
`apps/api/src/modules/notifications/index.ts` (export the invoice queue adapter), `packages/observability`
redaction list (the link path segment).

**Retry design (C1 — PENDING FOCUSED APPROVAL: it changes the approved hash-only storage of R1-16).** A random
token kept only as SHA-256 cannot be rebuilt, so a worker that crashes after minting the link but before or
during the send could not re-send the same link. The plan keeps the hash for lookup and adds **a sealed copy of
the token** so a retry re-sends the same link:

- `invoice_links` (0062) gains `token_sealed text NOT NULL`, sealed with the existing `SecretSealer`
  (`@eyadex/secrets`, AES-256-GCM). **Key — PENDING C1-Q2:** spec §8c.1 as proposed names `OUTBOX_SEAL_KEY`
  (already in the API and the worker; the invitations use it); the documented alternative is a dedicated,
  worker-only `INVOICE_LINK_SEAL_KEY` (`evidence/2026-10-15-finance-f1/c1-q3-and-key-comparison.md` §3). This
  plan does not choose. (The WhatsApp token uses a different key, `MAIL_PROVIDER_SEAL_KEY`.) The seal's `context` (GCM additional data) is
  `invoice_link:<clinic_id>:<link_id>:<notification_id>`, so a sealed value copied to another row never opens.
- **Lookup never uses the sealed copy:** `/i/<token>` hashes the presented token and calls
  `invoice_link_lookup(sha256)`; `invoice_link_lookup` and its NOLOGIN owner get **no** grant on `token_sealed`.
  Only `eyadex_app` (the worker) reads it; `eyadex_platform` has no grant on `invoice_links`.
- **Worker steps per ledger row attempt — PENDING C1-Q3.** Written below as path (a), spec §8c.1 as proposed
  (network never inside a DB transaction or lock). The documented alternative, path (b), keeps step 1 and then
  runs steps 2–3 inside the existing `whileLocked` ledger transaction, as every other notification kind does
  today (comparison: `c1-q3-and-key-comparison.md` §2). Under either path the link commits before any send,
  so the recoverability requirement holds: a retry re-sends the same URL, one live link per notification.
  1. Tx 1 (`withTenant`, short): lock the ledger row; if the invoice is void ⇒ mark `skipped`/`invoice_void`
     and stop. `SELECT … FROM invoice_links WHERE clinic_id = $c AND notification_id = $n FOR UPDATE`:
     - none ⇒ draw 32 random bytes (base64url token), insert `(id, invoice_id, notification_id, token_hash =
sha256(token), token_sealed = seal(token, context), expires_at = now + 14 days)`;
     - one, live ⇒ `open(token_sealed, context)`; if it opens and `sha256(token) = token_hash` reuse it;
     - one, but `SealOpenError` (the seal key was rotated) or expired ⇒ revoke it (`revoked_at = now`) and mint a
       fresh link for the same notification (the unique index is partial `WHERE revoked_at IS NULL`).
       Commit. The plaintext token now exists only in worker memory.
  2. Send over the network (email/WhatsApp transport) **after** Tx 1 committed, outside any transaction.
  3. Tx 2 (`withTenant`, short): record the outcome on the ledger row (`sent` / `failed` + reason), as today.
     A crash between 1 and 3 leaves the row `queued`; the next attempt re-enters step 1, finds the live link and
     re-sends **the same URL** — one link per notification, never two live links for one send.
- **Secrets stay out of logs and the outbox:** the outbox payload stays `{ notificationId }`; the token and the
  sealed value are never logged (the pino redaction list gains `token`, `tokenSealed`, `link`; the request log
  of `/v1/public/invoices/:token` logs the route pattern, not the path).
- Public route `GET /v1/public/invoices/:token` listed in `PUBLIC_V1_ROUTES` with a per-IP and per-token-prefix
  limit; lookup via `invoice_link_lookup(sha256(token))` then `withTenant`; audit actor `patient_link` (R2-7).
- If C1 is **not** approved, the alternative is "a retry mints a new link and revokes the old one" (hash-only
  kept): a crashed send could then leave the patient holding a link that no longer works.
