Status: manager accepted the Zod 3.25.76 baseline, including the datetime, worker-event, and Evolution-webhook extension. That acceptance was contracts 25 files / 523 tests, API 75 files / 775 tests, worker 25 files / 452 tests, `pnpm typecheck` 15/15 cached, `pnpm lint` 15/15 cached (0 errors, 11 existing web warnings), and targeted Prettier plus `git diff --check` exit 0. Manager review of the exact head, CI, staging, Socket, and Codex review have not passed. This note does not clear those gates and is not a security clearance.

Research time: 2026-10-26. Parsers compared: installed `zod@3.25.76` default export (`index.js` re-exports `./v3/external.js`) and installed `zod@4.6.6` default export (`./v4/classic/external.js`). Move api, worker, web, and contracts off `zod@3.25.76` onto the real `zod@4.6.6` parser after accepted inputs, parsed outputs, i18n messages, and the public HTTP envelopes still match. Raw Zod diagnostic codes in the contract tests are version evidence, not a project contract, and get two controlled updates at the pin. `packages/auth` is already on `4.6.6`. The three TanStack parent selectors stay. No `minimumReleaseAgeExclude`, no new scanner, no new direct dependency, no SQL, no production write, and no authorization change.

The compatible-patch audit on this tree, while `zod@3.25.76` was still installed, was 5 low, 11 moderate, 1 high, 0 critical (17). ## Datetime and standalone-parser extension

Measured on the exported schemas and the production parsers, installed `zod@3.25.76` only. Not a Zod 4 proof.

`firstAdminInviteLinkSchema` is the UTC frame (`email`, `token: null`, `expiresAt`). It accepts and returns unchanged: minute-only `2026-10-26T00:00Z`, seconds, fractional seconds, and leap-day minute-only `2024-02-29T00:00Z`. It rejects a colon offset, a compact offset, non-leap `2026-02-29`, month 13, 31 April, hour 24, leap second `:60`, and a value with no zone. An unknown key is stripped. `token` stays `null`.

`updateSubscriptionRequestSchema` is the offset frame and is strict. It accepts and returns only `expiresAt` for minute-only `Z`, `+03:00`, and `+0300`; seconds `+0300`; fractional compact `-0530`; in-range `+23:59`; legacy out-of-range `+24:00` and `+03:60`; and leap-day compact `2024-02-29T00:00+0300`. It rejects non-leap, bad month, bad day, hour 24, leap second, and no zone. An unknown key is `unrecognized_keys`. An empty body is `validation.required`. Duration plus `expiresAt` is `validation.oneExpiry`. `{ status: "trial" }` and `{ durationDays: 7 }` do not invent `expiresAt`.

A source count of `.datetime(` in `packages/contracts/src` is 70 calls on 68 lines. Five are `datetime({ offset: true })`: `appointments.ts:54`, `schedules.ts:91-92`, `platform-clinics.ts:27`, `onboarding.ts:121`. The other 65 are plain UTC `datetime()`. Worker adds two offset parsers (`branch-event.ts` `deactivatedAt`, `invitation-event.ts` `expiresAt`) and two UTC parsers (`reminder-rules.ts` `expiresAt`, `team-invite.ts` `expiresAt`). Zod 4's stricter RFC 3339 policy is not an approved business change.

Installed `zod@4.6.6` `v4/core/regexes.js` lines 103-105 require seconds on every qualified datetime (`Z` or an offset). Lines 101-102 allow only `±HH:MM` inside a clock range, so `+0300`, `+24:00`, and `+03:60` fail. A manager comparison recorded 6 UTC and 84 offset native acceptance deltas; a `z.regex` of 3.25.76 `datetimeRegex` kept all 324 acceptances and outputs. The later fix is one shared pure string-predicate pair, UTC and offset, taken from that regex. It must return the original string. Do not use `Date.parse`, coercion, colon insertion, or the native 4.6.6 datetime. Apply it to all 70 contract calls and the four worker datetime parsers, not only the five offset sites.

`zod-migration-events.spec.ts` freezes the six pure parsers. Loose ids (variant nibbles `0`, `1`, and `c`, uppercase, nil, max) come back unchanged. Offset parsers keep minute-only and compact offsets, including `+24:00`. UTC parsers keep minute-only `Z` and reject an offset. Invitation strips an unknown top-level key, returns `role: null` for `clinic.admin_invited`, and does not lowercase the address. The parsed invitation drops `expiresAt` after checking it. Reminder `daysLeft` stays `1..60`. Team invite requires a null row clinic. Mail test omits `slot` as `"primary"`, keeps `"fallback"`, and rejects version `0` and `1.5`. Notification copies the row clinic, requires it non-null, and rejects a clinic id in the payload because the object is strict. The row clinic is not itself parsed, so `row-clinic` is copied. Trailing newline ids fail `uuid()` today; a later `guid()` must not start accepting them.

`zod-migration-webhook.spec.ts` freezes `parseEvolutionWebhook`. `connection.update` with `data.state` `close` and `instance` `eyadex-` plus one of those loose ids returns `{ kind: "closed", clinicId }` with the id unchanged. A missing prefix, a bad id, a short id, and a trailing newline return `[]`. `state: "open"` and an unknown event return `[]`. `messages.update` with `ERROR` still returns `rejected` and the unmodified id. `SERVER_ACK` stays empty.

Stage 2 `guid()` replacement also covers those six worker parsers and `apps/api/src/modules/notifications/domain/evolution-webhook.ts` line 47. Contract `idSchema` coverage is not enough.

## Envelope code map

One shared function, called from the pipe and the filter, copies `path` and `code` only. Do not build a fake Zod 3 issue inside the v4 parser. Measured on 4.6.6 public issues:

- `invalid_format` → `invalid_string` (uuid, email, and a regex stand-in for compact offsets all use this code).
- `invalid_union` with the public `discriminator` set → `invalid_union_discriminator`. Without it, stay `invalid_union`.
- `invalid_value` with one `values` entry → `invalid_literal`. More than one → `invalid_enum_value` in that first map. No contract enum has a single option. A later follow-up splits the multi-option case by the value at the parse boundary; see Enum type code. Do not apply that split from `values.length` alone.
- every other `code` stays, including `custom`, `unrecognized_keys`, `invalid_type`, `too_small`, `too_big`.

`errors.spec.ts` line 125 stays `invalid_string`. The new subscription case stays `invalid_enum_value` at `["status"]`. A switch that skips this map fails those HTTP tests. The distinguishing fields are on the public issue. That map does not rewrite a raw `safeParse` result, so it cannot keep the contract-test diagnostic codes stable. Do not accept both codes in one assertion, and do not drop an assertion to make the pin pass.
